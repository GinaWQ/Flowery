## 1. Моя роль у команді

Як тімлід я відповідала за спільний каркас API, яким користуються учасники B і C, а також за свою частину ресурсів: відгуки та версію v2 API. Також я вела документацію і перевіряла роботу колег через Pull Request.

Мій розподіл:
- каркас API: blueprint, спільний формат помилок, підключення всіх модулів, Swagger, обробка помилок у JSON;
- ресурс «Відгуки»: список, створення, видалення з перевіркою ключа адміністратора;
- версіонування: `/api/v2/products`;
- Postman: колекція тестів і змінне середовище;
- документація: таблиця ендпоінтів відгуків.

## 2. Що зроблено

### 2.1. Каркас API (етап 0)

Гілка `feature/api-core`, Pull Request злито в `main`.

- `requirements.txt`: додано бібліотеку `flasgger` для автоматичної документації.
- `routes/api_core.py`: спільний blueprint `/api/v1`, функція `json_error()` для єдиного формату помилок `{"error": "текст"}` і ендпоінт `GET /api/v1/` з переліком ресурсів.
- Заглушки модулів для колег: `api_products.py`, `api_orders.py`, `api_customers.py`, `api_promo.py`. Кожна містить лише blueprint, щоб учасники могли працювати паралельно без конфліктів у `app.py`.
- `app.py`:
  - підключено всі blueprint;
  - додано Swagger-документацію на `/apidocs/`;
  - обробник помилок повертає JSON для адрес `/api/...`, а для сторінок сайту залишає звичайні HTML-сторінки;
  - для непередбачених помилок повертається код 500.

Коміти: `chore(api): додати flasgger до залежностей`, `feat(api): базовий blueprint, хелпер помилок і заглушки для команди`, `feat(api): підключення блюпрінтів, Swagger і JSON-обробка помилок`.

### 2.2. Ресурс «Відгуки» (`routes/api_feedback.py`)

| Метод | Адреса | Призначення | Коди |
|---|---|---|---|
| GET | `/api/v1/feedback` | Опубліковані відгуки | 200 |
| POST | `/api/v1/feedback` | Залишити відгук | 201, 400 |
| DELETE | `/api/v1/feedback/<id>` | Видалити відгук із заголовком `X-Admin-Key` | 204, 401, 403, 404 |

Реалізована валідація: імʼя і текст не порожні, текст не довший за 1000 символів, оцінка — ціле число від 1 до 5, email (якщо вказано) містить символ `@`. Для видалення перевіряється ключ адміністратора: без заголовка повертається 401, з неправильним ключем — 403.

Коміт: `feat(api): відгуки: список, створення, видалення з перевіркою ключа (401/403)`.

### 2.3. Версіонування (`routes/api_v2.py`)

Додано версію `/api/v2/products`. Вона повертає ті самі товари, але з іншими назвами полів (`title`, `price_uah`) і полем `in_stock`. Це демонструє, що старі і нові клієнти можуть працювати з API одночасно.

Коміт: `feat(api): версія v2 списку товарів (версіонування API)`.

### 2.4. Postman і документація

- Створено змінне середовище `Flowery Local` з `base_url = http://127.0.0.1:5000`.
- Створено колекцію `collection_A_feedback_v2.json` із запитами для успішних сценаріїв і помилок: створення відгуку, валідація рейтингу, видалення без ключа (401), з неправильним ключем (403), видалення двічі (404).
- У Tests для POST зберігається `feedback_id` у змінну середовища, тому наступні запити працюють із тим самим відгуком.
- Файли експортовано в папку `postman/` і додано до репозиторію.
- Створено `docs/api/feedback.md` з таблицею ендпоінтів.

Коміт: `cea09e1 test(api): колекція Postman для відгуків і v2, середовище Flowery Local`.

## 4. Труднощі та їх вирішення

1. **Проєкт у двох копіях.** Після завантаження архіву з GitHub у папці з'явилася копія `Flowery-main`, яка потрапила в репозиторій. Я перевірила, що git відстежує правильний корінь (`git rev-parse --show-toplevel`), порівняла папки (`diff -rq`) і перенесла в корінь тільки потрібні файли (`docs/`, `postman/`). Видалення дубля `Flowery-main` винесено в окремий PR, щоб не змішувати з моєю роботою.

2. **Файли помилок у Swagger і JSON.** Спершу помилки для неіснуючих адрес поверталися у вигляді HTML. Вирішено обробником у `app.py`, який перевіряє, чи адреса починається з `/api/`.

3. **Помилка 500 на `/api/v1/products` і `/api/v1/orders`.** Перевірка схеми бази (`PRAGMA table_info`) показала, що таблиці `products` і `orders` створено з іншою структурою, ніж очікує код API: у `products` немає колонки `stock`, у `orders` немає `subtotal` і `discount`. Причина в схемі учасника B (`schema/04_shop.sql`). Мій код API не змінювався, тому це питання передано B на виправлення. Після виправлення потрібно видалити `db.sqlite` і запустити сервер заново.

4. **Синхронізація з напарниками.** Щоб не було конфліктів, я створювала заглушки в спільних файлах і погодила порядок злиття: спершу каркас, потім B і C, потім мій PR.
